# 真实数据与可追溯性规范

## 1. 目标

项目中的每一个地图图层、面板数字、图表点、排名和文字结论，都应该能回答：

```text
它来自哪个文件或数据库？
使用了哪个字段、波段和年份？
经过了什么处理？
处理代码和参数在哪里？
它是原始值、清洗值还是派生值？
有哪些限制？
```

回答不了时，该内容不能作为正式结果展示。

## 2. 数据分层

### Raw 原始数据

- 用户提供的原始文件。
- 不覆盖、不改名、不直接编辑。
- 建议记录文件大小、修改时间和 SHA-256。

### Processed 处理数据

- 格式转换、编码修复、重投影、裁剪、重采样、缺失值处理后的结果。
- 文件名应能看出处理类型。
- 每次处理都要记录参数。

### Derived 派生数据

- 由多个指标计算的评分、等级、风险指数、变化率等。
- 必须有公式、权重来源、适用范围和解释。
- 页面上明确标注“派生/估算”，不能冒充实测值。

### Service 服务输出

- KQGIS WMS 输出的 PNG。
- Django 输出的 JSON/GeoJSON。
- 它们是传输和展示结果，不是新的原始数据来源。

## 3. 数据清单最低字段

在 `docs/数据清单.md` 中为每个数据集记录：

| 字段 | 说明 |
| --- | --- |
| 数据集 ID | 项目内唯一英文标识 |
| 原始文件 | 完整文件名，不必在公开页面暴露本机绝对路径 |
| 来源 | 用户提供、政府开放数据、实测、遥感产品等 |
| 获取日期 | 已知则填写 |
| 许可/署名 | 是否允许比赛展示和再发布 |
| 类型 | GeoTIFF、Shapefile、CSV、Excel、数据库等 |
| CRS | EPSG 与 WKT/名称 |
| 空间范围 | xmin、ymin、xmax、ymax |
| 时间范围 | 年/月/日及每个波段的含义 |
| 单位 | 数值字段和像元值单位 |
| NoData | 栅格无效值 |
| 字段/波段 | 字段名、波段号与业务含义 |
| 记录数/尺寸 | 矢量要素数或栅格宽高 |
| SHA-256 | 原始文件指纹 |
| 已知限制 | 缺失、精度、时效性、覆盖范围等 |

## 4. 空间数据专项规则

### 坐标系

- `.prj` 存在不代表一定正确，要读取并检查。
- 没有 CRS 时不得凭地图位置直接指定，应向用户或数据说明确认。
- 重投影必须记录源 CRS、目标 CRS、转换工具和重采样方式。
- 面积、距离计算应使用合适的投影坐标系，不能直接在经纬度上随意计算。

### GeoTIFF

- 记录宽、高、波段数、数据类型、仿射变换、CRS、范围和 NoData。
- 不把渲染颜色当作真实数值。
- 统计前剔除 NoData，并说明是否进行了缩放系数转换。
- 多波段文件必须建立“波段号→日期/指标”的证据表。

### Shapefile

- `.shp/.shx/.dbf` 缺一可能无法完整使用。
- 中文乱码先检查 `.cpg` 和 DBF 编码，不直接替换文字。
- 用稳定 ID、行政区代码或经过核验的名称做表格关联。
- 名称模糊匹配会产生误关联，必须输出未匹配和重复匹配清单。

## 5. 表格数据专项规则

- 保存原始列名，同时为代码建立明确字段映射。
- 识别空字符串、`-9999`、`N/A` 等缺失值表达。
- 检查重复键、年份缺口、异常值和单位变化。
- 排名必须说明升序/降序和并列规则。
- 平均值必须说明是算术平均、面积加权还是其他方法。
- 跨表合并后记录合并前后行数及未匹配项。

## 6. 派生指标规范

每个派生指标写一张说明卡：

```text
指标名称：
目的：
输入字段/栅格：
公式：
权重来源：
归一化方式：
单位：
输出范围：
缺失值处理：
适用场景：
不能代表什么：
验证方式：
```

如果权重只是项目团队设定，应写“项目设定权重”，不能写成行业标准。若没有来源和验证，优先展示基础指标，不强行创造综合指数。

## 7. 页面措辞规则

| 数据事实 | 可用措辞 | 禁止夸大 |
| --- | --- | --- |
| 历史年度遥感指数 | “历史遥感指标展示” | “实时监测” |
| 基于指标加权的风险分 | “派生相对敏感性” | “实测洪水范围” |
| 单次卫星观测 | “该时相影像结果” | “长期趋势” |
| 模型估算 | “模型估算/预测” | “实际发生” |
| 缺少最新年份 | “最新可用数据为……” | 用旧数据冒充当前数据 |

## 8. 模拟数据规则

正式页面和答辩默认禁止模拟数据。只有同时满足以下条件才可使用：

1. 用户明确同意。
2. 目的是测试组件或接口，不是伪装成业务成果。
3. 文件、接口和页面明显标注 `mock/demo/模拟数据`。
4. 模拟数据与真实数据目录分开。
5. 最终交付前删除或关闭模拟数据路径。

## 9. 数据处理记录模板

```markdown
## 处理任务 ID

- 日期：
- 操作者/脚本：
- 目的：
- 输入文件及 SHA-256：
- 输出文件：
- 工具与版本：
- 命令/代码位置：
- 参数：
- CRS 变化：
- NoData 处理：
- 计算公式：
- 处理前后记录数/尺寸：
- 验证结果：
- 已知限制：
```

## 10. 页面数据来源弹窗建议

数据来源弹窗至少展示：

- 数据集名称和原始文件名。
- 数据时间范围和空间范围。
- 原始/处理/派生分类。
- 地图服务名和图层名称。
- 派生公式摘要。
- “非实时”“非实测”等必要限制。

不要在公开页面展示本机用户名、完整磁盘路径、管理员账号或令牌。

## 11. 变更与审计

- 数据或公式改变时同步更新 API、页面来源说明、文档和测试。
- 保留处理脚本，不只保留处理后的结果。
- 不在代码审查之外手工改 CSV 数值或 KQGIS 内部数据库。
- 重要发布前重新生成数据清单和服务清单，避免文档过期。

## 12. 真实性验收问题

交付前逐项回答：

- 页面每个数字能否定位到数据行或计算代码？
- 地图每个图层能否定位到真实文件和 KQGIS 图层 ID？
- 年份控件是否真的改变对应年份的数据？
- 图表与地图是否使用相同指标定义和单位？
- NoData 是否被排除而不是当成 0？
- 派生指标是否明确标注？
- 是否仍有 mock、随机数或硬编码业务值？
- 数据来源和限制是否能被答辩者准确说明？
