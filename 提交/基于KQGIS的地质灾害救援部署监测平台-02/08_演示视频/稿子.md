## 第一部分：PPT 前期引入（00:00—05:10）

各位评委老师，大家好！我们展示的作品是《基于 KQGIS 的地质灾害监测救援部署系统——以吉隆口岸泥石流灾害为例》。

这项作品源于我们对地质灾害及救援工作的关注：当灾害发生后，如何让现场信息更清晰，让救援任务的分配与反馈更顺畅？这是我们希望通过这次实践探索的问题。

在进入系统演示之前，我们想先把视角放大，看一看我们赖以生活的自然环境正在经历怎样的变化，以及这些变化带给我们的思考。

我们生活在同一个地球上。山川、河流和气候，为日常生活提供了基础，也在持续发生变化。当这些变化与人类聚居、交通和生产活动相遇，自然风险就可能影响每一个具体的人。今天，我们团队想先基于这样的现实背景谈起。

经世界气象组织确认，我国2025年共出现43次区域暴雨过程，部分地区受到强降雨集中影响。气候与降水的变化，时刻提醒我们应持续关注环境风险。

面对这些真实的灾害，我们需要认真反思：风险变化能否更早被看见？救援展开后，信息能否衔接得更顺畅？防灾与救援涉及长期建设，也需要专业人员的现场判断。我们的团队也希望从能够具体实现的信息协同问题入手，支援现场行动。

带着这样的思考，我们把目光投向近期发生的吉隆口岸泥石流灾害。据央视网消息：2026年8月26日10时30分许，尼泊尔一侧发生冰岩崩塌泥石流，波及我国吉隆口岸。灾后国家二级救灾应急响应启动。这一具体事件，让我们进一步思考地理信息能怎样服务救援协同

这场救援有着非常具体的客观约束：通道受损，使人员和大型装备难以抵近；道路受损、通信与电力保障受扰，加上持续存在的次生灾害风险，都要求救援与监测同步推进。现场情况不断变化，
救援部署也需要及时调整，这对信息传递的时效性和多支队伍之间的协同性提出了更高要求。
针对这样的救援需求，我们项目将现场位置、队伍任务和进度反馈关联起来，帮助管理人员及时跟进现场情况，掌握各组任务进展，并根据最新反馈调整救援部署，为协同处置提供支持。

现场并不缺少专业人员的努力。国家减灾中心的公开报道展示了无人机监测、道路损毁调查和影像成果获取。随着资料不断增加，协同还需要回答：不同来源的信息能否指向同一处位置？新的现场反馈能否与正在开展的任务对应？这正是本作品所关注的问题。

此次吉隆口岸事件给了我们明确的选题启发。我们选择以这一地区为案例，制作了地质灾害监测救援部署系统。它是一次面向实际需求的实践。

基于前面的思考，我们依托赛事组提供的 KQGIS Desktop 和 KQGIS Server二次开发，完成了这套地质灾害监测救援部署系统。

接下来介绍系统的整体架构。我们将系统划分为数据层、服务层和应用层。
数据层主要包含遥感影像、专题矢量资料，以及队伍、任务和上报等业务数据。其中，SQLite 保存业务记录，图片作为文件独立存放，已有的 CSV 和 DBF 文件用于数据面板展示。系统直接读取现有资料
服务层由 KQGIS 地图平台和 Django 后端组成。KQGIS Desktop 用于整理地图，KQGIS Server 发布 WMS 地图服务；Django 负责身份校验、队伍管理、任务分配、阶段上报和图片上传。
应用层分为指挥决策调度者和救援组长端。指挥端使用 Vue 和 OpenLayers，指挥决策调度者可以查看地图、点击创建点位并分配队伍。救援组长端通过手机号登录，查看本组任务，上传图片并推进任务阶段，相关反馈再展示到数据大屏的对应点位中。
通过这样的架构，我们将地图展示与救援业务连接起来，形成从点位创建、任务分配到现场反馈的完整操作流程。

下面介绍系统的核心业务 E-R 图。
系统主要包含指挥决策调度者、救援队伍、任务点位和任务上报四类实体。指挥决策调度者保存账户信息，队伍保存名称和救援组长手机号，任务点位保存坐标与任务编号，上报记录保存图片路径、反馈内容和时间。
它们之间有三组主要联系。
首先，指挥决策调度者“创建”任务点位：一个指挥决策调度者可以创建多个点位，每个点位关联一个创建者。
其次，救援队伍“执行”任务：一个队伍可以先后承担多个任务，未分配点位则可以暂时没有队伍。
最后，任务点位“产生”任务上报：一个任务可以有多次反馈，每条反馈只属于一个明确的点位。
这样的设计将基础资料、任务状态和现场反馈分别保存，减少重复录入，并明确每条数据的归属，为指挥决策调度者与组长端的协同提供数据支撑。

接下来，基于以上的讲解，我们进入该项目的实际演示部分
## 第二部分：实际系统演示（05:10—13:00）

### 05:10—05:50　登录与整体界面

首先我们启动一键启动的脚本程序，启动并验证所有的端口是否打开，成功启动后会自动打开指挥决策调度端和救援组长端，但在本次演示中我们使用手机画面演示救援组长端的操作，旁边是我的手机投屏演示。

[画面：指挥决策调度者登录；进入智慧大屏。密码输入过程可遮挡或剪短。]

指挥决策调度者登录后，首先看到指挥大屏。页面中央是救援地区遥感影像，当前为吉隆口岸区域地图，左侧是与地图对应的灾害相关资料面板，上方是五类救援力量的入口，下方是经纬度坐标的实时显示。系统把“查看地理资料”和“发起救援调度”放在同一工作界面中，减少在多个页面之间反复查找的时间。

### 05:50—06:40　吉隆口岸多时相影像

[画面：在默认口岸影像上缩放、平移；打开影像选择，依次切换两三景，最后回到默认视角。切换后等待图像加载。]

大屏默认加载救援地区遥感影像，当前为吉隆口岸遥感影像。地图服务由 KQGIS Server 发布，前端使用 OpenLayers 进行交互。这里可以在已加载的遥感影像之间切换，并定位到所选影像的覆盖范围。不同时间的原始遥感影像放在同一个入口，便于演示时查看口岸及周边地貌。

### 06:40—07:40　左侧资料与县域专题图

[画面：指向四张资料卡及图表；点击“冰川资料”，展示吉隆县冰川图；再次点击返回口岸。再选择“冰湖资料”或“冻土资料”演示一次同样的切换。]

左侧目前展示冰川、冰湖、冻土和历史灾害区四类资料。面板上的记录数量和图表读取现有 CSV、Shapefile 文件。点击资料卡，地图就从救援地区遥感影像切换到灾害相关数据专题图像；再次点击，回到救援地区。这样，左侧数据和中间地图有明确对应关系。

### 07:40—08:20　救援类别与调度后台

[画面：指向地图上方五类救援组及“可分配/总数”数字；点击其中一类进入后台，展示队伍列表、详情，再点击右上角“返回”。]

地图上方分为抢险救援、医疗治疗、电力保障、地质监测、群众安置五类，当前数据库中有六支具体队伍。每类旁边的比例表示当前可接收任务的队伍数与该类别全部队伍数。点击任意类别可以进入调度后台，查看该类队伍和组长信息。指挥决策调度者可以维护队伍基础资料；这些队伍资料同时决定地图点位分配时的可选对象。

### 08:20—09:35　指挥决策调度者创建并分配点位

[画面：回到口岸地图，在已加载影像范围内单击一次；指向新出现的水滴标记；打开标记旁的小表单，选择一支事先准备好组长登录信息的队伍并确认分配。镜头停留在任务编号与图标变化处。]

下面演示一条救援任务。指挥决策调度者在口岸地图上单击，生成一个待分配点位。红色水滴表示这个点还没有交给具体队伍；点位由指挥决策调度者手动创建。鼠标靠近点位，就能在旁边的表单中选择具体队伍。确认分配后，系统生成唯一任务编号，任务进入“已分配任务，请尽快到达”的阶段，进度为百分之零。标记也从水滴变成对应救援类别的红底圆形图标，方便指挥决策调度者在地图上区分任务归属。删除点位需要二次确认，本次演示先保留任务继续流转。

### 09:35—11:15　组长手机端上报

[画面：切到安卓端或组长 Web 端。用刚被分配队伍的组长手机号登录，展示新任务编号、组名和当前阶段；点击“上报下一阶段”；选一张公开可用的演示图片上传；再点击“上报任务完成”。各步操作后等待页面刷新。]

现在切到组长任务端。组长使用后台登记的手机号登录，只处理分配给自己队伍的任务。刚才的任务已出现在当前任务中，可以看到任务编号、队伍和阶段提示。到达后，组长点击“上报下一阶段”，任务由“已分配”进入“任务中”，进度显示百分之五十。现场图片可以单独上传，不必为了上传图片强行推进阶段；这里上传的是一张演示图片。任务处理完毕后，再由组长上报完成，进度达到百分之百。

### 11:15—12:15　大屏联动与闭环

[画面：切回指挥决策调度者大屏，等待约 10 秒同步；悬停或点击刚才的点位，展示任务编号、阶段、进度和图片；指向变绿的类别图标。]

回到指挥决策调度者大屏，点位信息会定期同步。鼠标靠近标记，可以查看对应组长上报的任务编号、进度和图片。完成后，图标保持救援类别形状，但底色由红变绿，表示该任务已经结束。这样一来，指挥决策调度者建点、分配队伍、组长上报以及大屏查看，形成了一条可追踪的操作闭环。上方可分配队伍数量也会随任务占用情况更新。

### 12:15—13:00　技术总结与结束

[画面：依次闪回口岸影像、县域专题图、后台队伍详情、绿色完成标记；最后停在大屏全景和作品名称。]

作品的核心特点有三点：第一，以 KQGIS server发布的地图服务为底座，把救援地区遥感影像和灾害相关数据统一发布，本次演示中将口岸影像和吉隆县专题资料发布并连接到同一大屏；第二，把指挥决策调度者的空间点位与数据库中的队伍、唯一任务编号关联起来；第三，让救援组长端的阶段和图片上报回到指挥大屏，直观呈现调度结果。当前版本面向本地演示和流程验证。未来可以在真实监测数据接入、任务审核和安全部署方面继续完善。以上就是我们的作品演示，谢谢各位评委。
